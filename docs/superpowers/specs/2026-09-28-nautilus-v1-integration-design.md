# Quant Core + NautilusTrader v1.231.0 integration design

Status: implementation design, 2026-09-28. Scope ends at local historical backtest and local paper. No exchange authentication, live order routing, push, merge or release. Work occurs on integration/nautilus-v1, branched from the verified clean Task0 closure HEAD. The 2026-09-27 Phase9 Spec and approved implementation plan remain authoritative for Phase9 domain behavior; this document only specifies prerequisites and Phase10/11 adapter-facing behavior.

## 1. Ownership and acceptance

Quant Core owns Phase1–8 market facts, quality/authority/provenance, point-in-time source projections, immutable EvaluationSnapshot, Phase9 evidence/pattern/Jev/Python decision, research feature definitions, risk approval, idempotent intent record and audit. Nautilus owns simulation clock, order/fill and position lifecycle, portfolio accounting except for the explicitly identified v1 funding gap, and the local paper execution substrate. One account has one active execution owner. Phase1–9 do not import Nautilus symbols. The first engine is pinned to exactly 1.231.0 in an isolated integration environment. Nautilus v2 prereleases and all real exchange credentials are excluded.

A candidate is not an order. The execution boundary consumes only a current eligible DecisionCandidateV1 whose append-only effective status is ACTIVE, TTL is future, versions and input_snapshot_hash are supported, and whose evaluation snapshot reference is immutable. If Phase9 remains unfinished, fixture-driven isolated adapter tests must not claim formal Phase9 or strategy acceptance. Future Live requires separate authorization.

## 2. Existing closure and two prerequisite fixes

Every Phase9 task begins by validating the existing Task0 compatibility gate. The closure commit stays 2f9cbab0ed8b0371e467c7b69d723439a5cf112e. If a protected file changes, rerun four mapped suites and regenerate their evidence against the new protected tree digest; do not change the closure anchor or weaken the gate. No required skip/xfail.

Instrument identity is a typed core-domain record derived from validated Phase1 symbols metadata: core_symbol, canonical_symbol, market, base/quote/settle assets, contract type, and explicit per-venue symbol mappings. BTCUSDT is a core/venue spelling; BTC-USDT-PERP is the canonical identity. Phase9 Phase2 aggregate, Phase3 flow/CVD/gap and Phase4 liquidation source queries resolve canonical identity through this boundary using the persisted Phase1 symbol record. Missing, ambiguous, offline, mismatched market or unsupported contract metadata fails closed. No permanent suffix heuristic or Nautilus class enters Phase1–9. A separate execution binding maps canonical identity plus venue/account to the exact Nautilus InstrumentId string discovered/validated from the pinned adapter or local simulated instrument; the registry rejects unknown/duplicate bindings.

OI quality is computed from the actual normalization contract, not the string VERIFIED. Valid AVAILABLE methods are base_quantity_times_mark_price, contracts_times_multiplier_times_mark_price and exchange_reported_quote_notional when persisted numeric fields, raw unit, mark and timestamps are consistent with the Phase2 producer contract; multiplier provenance is checked from the instrument binding when available. NOT_AVAILABLE/STALE/ERROR retain their status. Unknown method, inconsistent unit/value or unverified unit remains PARTIAL/UNKNOWN or fails validation according to the frozen evidence rule; it is never silently promoted. DecisionCandidateV1 remains the exact frozen dataclass in quant_phase9.contracts. It contains no entry, stop, size, leverage, order or framework type. Its input_snapshot_hash is not renamed. The stored EvaluationSnapshot digest is exposed to downstream consumers via a separate reference envelope. Existing Phase9 Tasks 1–9 are implemented in their approved order, including typed policy/approval, evidence, pattern, deterministic decision, atomic persistence, migration role separation, bounded Engine, typed replay and final acceptance. Formal Phase9 approval behavior follows the approved plan; no fabricated approval identity or hidden auto-tuned thresholds. A genuine approval conflict will be surfaced as a blocker rather than relaxed.

## 4. Canonical features and research

CanonicalFeatureV1 is immutable and versioned: definition ID/digest, canonical instrument, value and unit, source/authority/status/quality/coverage/provenance/source_ref, event/window time, received/processed/known_at, revision and freshness policy. A feature's value is visible at t only when event/window end and known_at are <=t and the source status is permitted. Backward-only as-of joins; missing or UNKNOWN never becomes zero or neutral. Existing Phase9 EvaluationSnapshot projections and ResearchFrame use the same pure feature projector and version map; research does not mutate a frozen snapshot or rescan it after evaluation. Mutable/upserted old rows without historical availability revisions are marked PIT_UNVERIFIED.

The first five hypotheses only: Price+OI, Price+OI+Funding, Price+OI+Taker Flow, Breakout+OI+CVD, Liquidation+OI Reset+Flow Reversal. Price-only control, common eligible cohort, chronological walk-forward splits, overlap purge/embargo, symbol/regime coverage, predeclared costs and out-of-sample evidence are required. Liquidation PARTIAL cannot support a complete-volume threshold. Directional taker UNKNOWN cannot support reversal. Research results do not automatically change production policy. Offline data uses immutable Parquet manifests; existing PostgreSQL retains operational/audit rows. No Kafka, Redis, ClickHouse or new data service.

## 5. Framework-neutral execution contracts

ExecutionIntentV1 is an immutable approved risk result: intent_id, decision/evaluation/snapshot references, canonical instrument/venue/account/mode, LONG or SHORT, UTC created_at/valid_until, exact approved quantity and unit, reference quote/as_of, maximum notional/margin/leverage, entry type/price/TIF/spread/slippage bounds, stop/protection instructions, risk budget amount/currency, policy versions/hash, deterministic content digest and stable client-order identity. Required fields cannot be null merely to make a framework call pass. Conservative rounding cannot increase risk beyond approved constraints. Intent uniqueness, risk-budget reservation and mapping to external IDs are durable in PostgreSQL.

ExecutionResultV1 is an append-only event with intent/execution/order IDs, external refs, status (ACCEPTED, PARTIALLY_FILLED, FILLED, CANCELLED, REJECTED, UNKNOWN), requested/cumulative/remaining quantity, average price, maker/taker fee, funding cash separately, protection state, event/received times, adapter version and reason. Acceptance is not fill. A partial fill followed by cancel leaves a position and requires protection.

PositionSnapshotV1 identifies account/venue/canonical instrument/mode/side, actual net quantity and unit, entry, equity/available balance, margin, mark, unrealized and realized trade PnL, fees, settled funding, protection status, source order/fill IDs, reconciliation status, as_of and version. Missing account or stale position is UNKNOWN, never zero. ExecutionAdapter Protocol provides capabilities, preflight, submit, cancel/amend, execution event stream, position snapshot and reconciliation. An unsupported exchange feature or changed quantity rejects preflight. Core has no Nautilus imports; only the pinned implementation translates to Nautilus objects.

Risk Policy owns the economic decision: candidate lifecycle/TTL, quote freshness, venue instrument bounds, position/margin snapshots, max notional/exposure/loss, concurrency and protection. It creates and durably reserves an intent atomically; adapter cannot resize upward. When a send times out, mark UNKNOWN and query by stable client ID/order/fill/position before any retry. At-least-once delivery is expected; exactly-once exchange execution is not claimed. DB unavailable means no new exposure. Existing protected positions continue to be managed by the single order owner.

## 6. Funding, costs and replay

Nautilus v1 has no verified built-in perpetual funding cash settlement. A pure FundingAccounting calculator consumes Quant canonical funding observations, settlement boundary, actual position held at boundary, mark price, unit/currency and source availability. It emits an idempotent payment keyed by account+instrument+boundary with paid/received sign. Thin backtest and local Sandbox drivers apply cash changes through the v1 simulated exchange and verify account-state effects; a separate shared ledger adds funding to net PnL because account cash adjustment does not by itself amend Position.realized_pnl. Missing rate, mark, boundary or position is unresolved, not zero. The same calculation and payment key is used across replay and paper, with no future settled rate in earlier features.

Cost assumptions include venue-specific historical maker/taker schedules, spread, slippage and latency. Bar-only simulations declare synthetic liquidity and conservative ambiguous intrabar fills; no candle-close perfect execution claim. Funding, fees, trade PnL and balance are reconciled separately. The BTC/ETH sample must cover LONG and SHORT and at least trend continuation plus breakout or reversal via deterministic fixture if authentic Phase9 signals are absent. Losses are reported, not optimized away.

## 7. Local paper, restart and resources

Local Paper uses only a deterministic public/synthetic feed and Nautilus Sandbox; it contains no production exchange client or private credential. A real process-stop/process-start test uses disposable PostgreSQL for intent/order/result/position mappings. Before shutdown it creates an order/position, persists the mapping, then restarts the worker and reconciles against its durable local simulated account/order/fill state. If the pinned Sandbox cannot preserve/reconstruct those facts without a custom persistent adapter, the gap is explicit and the restart gate is BLOCKED; a mocked repository unit test is insufficient. Recovery pauses new entries until unresolved intent/order/position links are settled. Account-level fencing prevents two active execution owners.

PostgreSQL <=768 MiB, Collector <=256 MiB, Engine aggregate <=384 MiB remain unchanged. Record process RSS, peak RSS and container memory during the spike and acceptance. A separate process/container budget requires explicit revised architecture and cannot be smuggled in. No current quant-engine, quant-postgres or agentops container may be modified; use isolated loopback disposable PostgreSQL and remove it after tests.

## 8. Acceptance and failure labels

Each gate emits measured evidence rather than self-declared PASS: core contract fixes, Phase9 compatibility/final deterministic acceptance, feature/no-lookahead, pinned Nautilus backtest, funding/cost ledger, adapter/risk, local paper, process restart/reconciliation and peak RSS. Required tests have zero skips. Report COMPLETE only if every required gate passes within resource limits; otherwise PARTIAL/BLOCKED with numeric findings and runnable instructions. Real live trading remains false.
